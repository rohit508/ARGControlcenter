# Project Context — Read This First

This file exists so a new Claude/agent session (with zero prior context) can immediately
understand the backend, database, and deployment setup without re-discovering it from scratch.
If the user says "database query likh do" / "yeh query bana do" / asks about deployment,
credentials, or how any of this is wired together — everything you need is below.

## What this project is

An ERP web app (`Enterprise ERP`). Two services:
- `client/` — React + Vite frontend, deployed on **Netlify**
- `server/` — Node/Express/TypeScript API, deployed on **Railway**

Repo: `rohit508/ARGControlcenter` on GitHub, `main` branch, deploys auto-trigger on push.

## Database: PostgreSQL on Neon (NOT SQLite anymore)

This project was **migrated from SQLite (better-sqlite3) to PostgreSQL (Neon) in August 2026**.
Full migration history, every decision made, and every issue hit is recorded in
[`postgres-migration-plan.md`](./postgres-migration-plan.md) in this same folder — read that
file if you need the "why" behind anything below.

  `schema.core.ts`, `schema.pmo.ts`, `schema.phase2.ts`, `schema.phase3.ts`,
  `schema.employeeTasks.ts` (all re-exported via `schema.ts`)

  departments, employee_task_assignments, employee_tasks, employees, issues, journal_entries,
  journal_lines, kb_articles, kpi_snapshots, leads, leave_requests, lessons_learned,
  lookup_lists, lookup_values, maintenance_logs, meeting_attendees, meetings, milestones,
  notifications, opportunities, permissions, po_lines, production_orders, project_shares,
  projects, purchase_orders, refresh_tokens, risks, role_permissions, roles, stock_items,
  stock_levels, stock_transactions, tasks, tickets, user_roles, users, vendors, warehouses,
  work_centers, workflow_actions, workflow_definitions, workflow_instances`
- **Local dev connection string**: in `server/.env.local` as `DATABASE_URL` (gitignored, never
  committed). Also live in `server/.env` (also gitignored) since local dev now points at Neon
  too — there is no more local SQLite file in active use (`server/dev.db` still exists on disk
  as a pre-migration safety backup, but the running app does not read it).
- **How to run a one-off query against the database** (from `server/` directory):
  ```bash
  node -e "
  require('dotenv').config({ path: '.env.local' });
  const { Client } = require('pg');
  const client = new Client({ connectionString: process.env.DATABASE_URL });
  client.connect()
    .then(() => client.query('YOUR SQL HERE'))
    .then(res => { console.log(res.rows); return client.end(); })
    .catch(err => { console.error(err.message); process.exit(1); });
  "
  ```
  This is the pattern used throughout this project's history for ad-hoc DB inspection — prefer
  it over spinning up a new script file for a single query.
- **Polymorphic tables to know about**: `comments` and `attachments` link to other entities via
  `entity_type` (text, e.g. `'employee-task-assignment'`, `'project'`) + `entity_id` (integer),
  not a normal foreign key. Always check `SELECT DISTINCT entity_type FROM comments` if unsure
  what values are in use before writing a join.
- **Code prefixes**: `employee_tasks.task_code` uses `ETSK-####`, `tickets.ticket_code` uses
  `TCK-####`, `employees.employee_code` uses `EMP-####`, `projects.project_code` uses
  `PRJ-####`. Generated by `server/src/lib/codeGenerator.ts` (`nextCode()`, async — must be
  awaited).

## Passwords / credentials — read before anyone asks "asli password kaise nikalein"

**Passwords cannot be extracted from the database, ever, by anyone — this is not a tooling
limitation, it's how bcrypt hashing works (one-way).** `users.password_hash` contains a bcrypt
hash (`$2a$10$...`), which can only be *verified* (does this plaintext match this hash?), never
*reversed* back into the original plaintext.

The only way to know a user's actual password:
1. **`server/CREDENTIALS.local.md`** (gitignored, never commit) — lists every seeded employee's
   plaintext password, generated once by `server/src/db/seed.ts` at seed time. Pattern:
   password is always `<email-username-part>@demo123`, e.g. `shehbaz.ahmed@erp.local` →
   `shehbaz.ahmed@demo123`. This is deterministic, so it's reconstructible from the email alone
   even without opening the file.
2. **If a password needs to change**, it must be *reset* (bcrypt-hash a new value and `UPDATE`
   the row), not recovered. There is currently no forgot-password/reset-password API endpoint
   in this app (`server/src/modules/auth/` only has login/refresh/logout/me) — a reset today
   means either an ad-hoc `UPDATE users SET password_hash = ...` (with a freshly bcrypt-hashed
   value, `bcryptjs` is already a dependency) or building a real reset flow.

## Deployment

- **Backend (`server/`) → Railway**, NOT Render, despite `render.yaml` still sitting in the repo
  root. `render.yaml` is inert/unused — Render's free tier started requiring card verification
  partway through this project's deploy, so the deploy moved to Railway instead (which already
  had working `railway.json` config files from an earlier point in this project's history).
  Don't assume `render.yaml` reflects what's actually live.
- **Production URL**: `https://argcontrolcenter-production.up.railway.app`
- **Frontend (`client/`) → Netlify**, config in `client/netlify.toml`, unaffected by any of the
  database migration work.
- **Railway config**: `server/railway.json` — build: `npm install --include=dev && npm run
  build`, start: `sh scripts/deploy-start.sh`.
- **`server/scripts/deploy-start.sh`** on every deploy: runs `npm run db:push` (Drizzle
  non-destructive schema sync against Neon — adds missing tables/columns, never drops/truncates),
  then seeds demo data **only if** the `users` table is empty (checked via
  `server/scripts/has-existing-data.ts`), then starts the server.
- **Environment variables live only in the Railway dashboard** (Variables tab), not committed
  anywhere: `DATABASE_URL` (Neon connection string), `CORS_ORIGINS`, `JWT_ACCESS_SECRET`,
  `JWT_REFRESH_SECRET`, `NODE_ENV=production`. If production ever breaks with a DB connection
  error, check these first — Railway sometimes pre-populates its own placeholder `DATABASE_URL`
  that silently overrides what you'd expect.
- **Known gotcha already hit and fixed**: Railway (and Render, and most PaaS) sit in front of
  the app as a reverse proxy adding an `X-Forwarded-For` header. Express's `trust proxy`
  defaults to `false`, and `express-rate-limit` throws on *every single request* if that header
  is present but Express isn't told to trust a proxy — this silently 502s the entire app even
  though the server logs show it booted fine. Already fixed in `server/src/app.ts` via
  `app.set("trust proxy", 1)` when `NODE_ENV === "production"`. If you ever see a fresh deploy
  boot cleanly in logs but 502 on every HTTP request, this is the first thing to check.
- **Health/readiness endpoints**: `GET /api/v1/health` is pure liveness (never touches the DB).
  `GET /api/v1/ready` actually queries Postgres (`SELECT 1`) — use this one to confirm the DB
  connection is actually working, not `/health`.

## Backend architecture quick map

- `server/src/app.ts` — Express app factory, all route mounting, middleware order
- `server/src/server.ts` — entry point, binds port, graceful shutdown, cron scheduling
- `server/src/env.ts` — fail-fast env var validation (reads `process.env` at import time — this
  is why `dotenv/config` must be imported before anything else touches `env.ts`)
- `server/src/db/` — Drizzle schema + `client.ts` (the `pg.Pool` + `drizzle` instance, exports
  `db` and `pool`)
- `server/src/modules/*/` — one folder per business module (routes + services), ~24 modules:
  auth, projects, tasks, risks, issues, budget, change-requests, milestones, meetings,
  action-items, lessons-learned, kpi-engine, config, gantt, workflow, resources, crm, finance,
  procurement, hr, inventory, manufacturing, assets, helpdesk, analytics, employee-tasks,
  employees, departments, attachments, rbac
- `server/src/lib/` — shared: `crudFactory.ts` (generic CRUD route builder), `codeGenerator.ts`
  (`nextCode()`), JWT helpers, RBAC scope resolver, audit logging
- Auth: JWT access + refresh tokens (`jsonwebtoken`), passwords via `bcryptjs`, RBAC via
  `roles` / `permissions` / `role_permissions` / `user_roles` tables
